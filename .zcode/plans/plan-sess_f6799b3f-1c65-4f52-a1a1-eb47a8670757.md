## 补全后端游戏管理 API 计划

### 背景与目标
前端已写好,调用 8 个后端端点,但只有 3 个存在(/、/health、/api/providers)。游戏引擎(orchestrator/werewolf)完整可复用,只差一层 API + 持久化。前端是纯 3 秒轮询(无 WebSocket),大大简化后端。

### 核心设计决策
1. **持久化用 JSON 文件**(非 SQLite):暑假项目,数据量小(每局一条记录),JSON 文件最简单,无需建表/迁移。存 `backend/data/games.json`。
2. **游戏在后台 asyncio.Task 运行**:`POST /api/games` 创建后用 `asyncio.create_task(orchestrator.run_game())` 后台跑,主线程立即返回。orchestrator 引用存在内存字典 `_games` 里,status 端点实时读 `orchestrator.game.state`。
3. **不引入 WebSocket**:前端不用,纯轮询足够。

### 要补的 5 个端点(对应前端 client.ts)

| 端点 | 做什么 |
|---|---|
| `POST /api/games/` | 转 player_configs→orchestrator config;5人校验;创建后台 task;持久化 initialized;返回 CreateGameResponse |
| `GET /api/games/` | 从存储读所有游戏→ListGamesResponse |
| `GET /api/games/stats` | 汇总存储数据→StatsResponse(**必须在 `{game_id}` 路由前注册**) |
| `GET /api/games/{game_id}/status` | 读内存中 orchestrator.game.state;`voting`→`vote` 映射;注入 total_cost;返回 GameStatusResponse |
| `GET /api/games/{game_id}/result` | 合并 GameResult + player_costs + total_cost;返回 GameResultResponse |
| `DELETE /api/games/{game_id}` | 从存储删;取消运行中 task |

### 文件结构(3 新建 + 1 改)
| 文件 | 类型 | 内容 |
|---|---|---|
| `backend/app/api/__init__.py` | 新建 | 空包标记 |
| `backend/app/api/schemas.py` | 新建 | Pydantic 请求/响应模型,严格匹配前端 types/api.ts |
| `backend/app/api/game_manager.py` | 新建 | 游戏生命周期管理:内存 task 字典 + JSON 持久化 + 状态查询/成本合成/阶段映射 |
| `backend/app/api/routes.py` | 新建 | FastAPI APIRouter,6 个端点 |
| `backend/app/main.py` | 改 | include routes.router |

### 关键实现细节(从 Explore 调研得出)

**1. 配置转换**(`POST /api/games`)
前端发 `{player_configs: [{player_id, provider?, model, base_url?...}], seed?}`,
orchestrator 要 `{players: [id], model_configs: {id: cfg}, game_id, seed}`。
转换:players = 提取 player_id;model_configs = 以 player_id 为 key 的字典。

**2. 5 人校验**:`werewolf.py:26` 强制恰好 5 人。在 POST 端点提前校验,返回 422 而非 500。

**3. 阶段映射**:引擎 `GamePhase.VOTING="voting"`,前端要 `"vote"`。在 game_manager 的 status 构建里做 `{"voting":"vote"}` 映射。

**4. 成本合成**:`GameResult.to_dict()` 不含成本。手动从 `orchestrator.agents` 的 `model_client.get_total_usage()["estimated_cost"]` 聚合出 player_costs 和 total_cost。

**5. 状态生命周期**:`initialized`(create后) → `running`(task开始) → `completed`/`error`(task结束)。task 结束的回调里更新存储。

**6. 路由顺序**:`/api/games/stats` 必须在 `/api/games/{game_id}` 前注册,否则 "stats" 被当 game_id。

### 验证(不花 API 钱)
- 启动后端,`curl` 测各端点的空状态(list 空、stats 全 0)。
- 用 DeepSeek key 跑一局**真实对局**经 API:create → 轮询 status 看实时变化 → completed 后取 result 看成本。这是端到端验证,证明 orchestrator 在后台 task 跑通且状态可被轮询。
- 前端 `tsc --noEmit` 确认类型仍干净。

### 不在本次范围
- ❌ WebSocket(前端不用)
- ❌ 事件流/发言详情端点(前端当前不显示,引擎已采集,留作未来)
- ❌ SQLite(用 JSON 替代,够用)
- ❌ 前端观战界面增强(发言/投票展示)——独立后续

### 风险与回退
- 后台 task 异常要捕获,标记 error 状态,否则前端永远 running。
- JSON 文件并发写:用 asyncio.Lock 保护,或简单同步写(数据量小,可接受)。
- 在新分支 `feature/game-api` 做。
